# 语音包导入失败状态须等待回滚完成

全量检查发现 `pyvenv` 缺失测试偶发读取不到旧 `config.toml`。这与已修复的成功终态过早问题不同：失败分支在旧包回滚完成前就发布“失败”。主会话接管这处有确定性反例的局部修补，未改媒体设备功能。

## 完整逻辑

1. **链路**：`src/voice-packs.js` 的异步导入 → `list()` 状态 → 管理页面或测试等待器；`startImport` 也靠终态判断能否再次导入。旧包先移到 backup，再安装；出错需要等待清理与恢复 rename。
2. **机制**：旧代码在 catch 开头标 `phase=失败`，消费者立即以为文件已稳定；事实上 catch 仍 await 清理/回滚。读配置可能 ENOENT，新导入也可能与回滚竞争。现在先显示“处理失败，正在恢复旧包”，直到成功恢复或明确回滚错误后才发布失败终态。保留原 code/hint 和 backup 路径。
3. **爆炸半径**：一个宿主进程，两类状态读者 × 可见错误 1；触及语音包文件替换时序，不读取密钥、不调用模型、不打开设备。回滚失败仍暴露旧包位置，不自动删除旧包。
4. **取舍**：延迟测试或增加重试只能遮住竞态；将终态后移两处赋值即可修复消费者共同契约，选择后者，不新增任务调度层。
5. **生效与重启**：DSH/控制台的 voice-packs 读者需重启；仅失败生命周期改变，安装参数和成功路径不变。
6. **验证**：测试阻塞真实 backup→target 的最终 rename，在屏障期间读取 list 必须不是失败；放开后等待实际恢复，验证失败 code、旧配置完全一致。旧实现确定性失败，新实现 `node scripts/test-voice-pack-import.mjs` 9/9 通过，日志 `.local/evidence/full-integration/voice-import-failure-order-{before,after}.log`。全量审计另随集成检查执行。
7. **回滚与残余**：`.local/backups/voice-import-failure-order/` 保存两文件，按旧字节恢复再重启即可；没有真实导入用户语音包或验证真实 TTS。既有导入回滚异常的 code/hint 仍保留。
